\section{Evaluation}
\label{sec:evaluation}

The evaluation is designed to distinguish four questions that are easy to conflate in an autonomous storage system:
\begin{itemize}[leftmargin=*]
  \item \textbf{RQ1: Safety under uncertain evidence.} Does the controller avoid unsafe and unnecessary actions when health signals are noisy or transient?
  \item \textbf{RQ2: Recovery effectiveness.} Does closed-loop control reduce the amount and duration of data exposed to elevated device risk without excessive data movement?
  \item \textbf{RQ3: Foreground interference.} For comparable completed maintenance work, does feedback reduce application tail-latency impact relative to fixed background budgets?
  \item \textbf{RQ4: Adaptation and mechanism value.} Which components---confirmation, cooldown, pressure feedback, and outcome feedback---account for the observed behavior under workload and health shifts?
\end{itemize}

\subsection{Experimental platform}
The control-plane and mounted-workload experiments run on a dual-socket Intel Xeon Gold 6138 host with 40 physical cores (80 hardware threads) and two NUMA nodes, using Linux 7.0.0-28 on x86-64. The experiment workspace resides on an Intel SSDPELKX960G8D NVMe device. To exercise the host-volume backend with distinct logical failure domains without repartitioning production disks, we create seven independent 16-GiB sparse images, format each as ext4, mount them separately, and use the seven mountpoints as \argosfs{} host disks. Distinct mount device identifiers make them distinct host-backend failure domains. Unless stated otherwise, the file-system layout is $(k,m)=(4,2)$, leaving one additional device available for evacuation and rebalance experiments.

Foreground experiments mount the host volume through the real \argosfs{} FUSE frontend. The retained data manifest records the evaluated software revision. The implementation description and completed non-performance results in this draft correspond to \argosfs{} commit \texttt{a52f6d2}; future paired measurements will use and report one frozen revision.

A separate device-mapper harness uses three loop-backed block devices with a $(2,1)$ layout to inject deterministic \texttt{dm-error} failures and raw data corruption. This harness validates the underlying block error, degraded read, repair, and journal behavior. As described in \cref{sec:prototype-scope}, it is substrate validation rather than a raw-backend \autopilot{} experiment.

\subsection{Health traces and fault traces}
We use deterministic synthetic traces with separate observation and ground-truth failure streams. The completed policy-replay artifact contains 100,000 seeded traces: five cohorts of 20,000 traces covering a single transient false-positive observation, two consecutive false-positive observations, critical failure, intermittent failure evidence, and sustained failure evidence. The same traces are replayed across the full controller and all baseline/ablation policies. The full-controller rows invoke the production Rust risk-memory and drain-decision functions directly; baseline and ablation rows are harness policies.

A broader parameter sweep over false-positive rate, missing observations, and correlated multi-device events remains part of the planned RQ1 artifact. We also plan a separate replay of the Q1 2026 Backblaze Drive Stats release \citep{backblaze2026q1}. The first remote-stream attempt terminated after day 62 of 90, so no statistic from that incomplete run is reported here. Once complete, that replay will retain SMART fields that map directly to the prototype health adapter and use the published failure label as outcome ground truth; the fixed \argosfs{} risk heuristic is not trained on the replay data.

For file-system-level fault injection, the deterministic matrix covers critical risk, moderate risk requiring confirmation, insufficient redundancy, cooldown after action, an added empty device that creates skew, and single-shard corruption. Every case verifies post-action consistency and content hashes. Device-mapper tests additionally inject an actual EIO device and byte-level corruption below the file-system interface.

\subsection{Baselines}
\input{tables/evaluation-matrix}

\paragraph{Reactive.} The system does not proactively drain on health evidence. It repairs only after an actual device failure becomes visible. This baseline measures the value of acting before failure.

\paragraph{Periodic.} Scrub and rebalance run at fixed intervals and fixed windows, while health evidence does not trigger drain. This captures a conventional timer-driven maintenance policy.

\paragraph{Fixed threshold.} This is the most important baseline. It receives exactly the same risk stream as \autopilot{} and invokes the same maintenance primitives, but a predicted-failure sample immediately triggers a drain attempt, routine work uses fixed windows, and there is no persistent confirmation, cooldown hysteresis, outcome adaptation, or foreground-pressure reduction. It tests whether the proposed controller is more than a threshold wrapped around existing tools.

\paragraph{Oracle.} The oracle knows injected or labeled failure times in advance, but uses the same file-system safety gates and maintenance primitives. It schedules the earliest safe proactive evacuation that fits the experiment's maintenance budget. The oracle is an upper bound, not a deployable competitor.

\subsection{Metrics and statistical protocol}
An \emph{unsafe action} is any controller-issued mutation that violates the experiment's predeclared survivability or consistency condition: draining when the layout-width precondition is false, making previously readable ground-truth data unavailable, or continuing a mutating controller chain after an injected metadata conflict. We separately report \emph{unnecessary drain rate}, the fraction of drained devices whose synthetic risk episode resolves without the ground-truth failure window, and \emph{pre-failure protection rate}, the fraction of predictable failures for which evacuation finishes before the injected failure.

RQ2 reports risk exposure from \cref{eq:risk-exposure}, time from first actionable risk to a safe post-maintenance state, duration in degraded state, repair completion time after actual faults, and logical/physical bytes moved. Each trace is paired across policies. Composite risk exposure is always shown beside the primitive metrics to avoid hiding behavior behind one weighting function.

RQ3 reports throughput plus P50, P95, P99, and P99.9 request latency measured outside \autopilot{} by the workload generator. Each performance configuration has a 120-second warm-up and 300-second measurement interval and is repeated ten times in randomized policy order. We report medians and 95\% bootstrap confidence intervals; paired policy differences are bootstrapped over matched repetitions. The same maintenance target---files scrubbed, files rebalanced, or bytes evacuated---must complete before comparing foreground cost. A policy that achieves low latency by doing less maintenance is not counted as a win.

When a safety experiment observes zero violations in $N$ independent seeded traces, we additionally report the conventional rule-of-three 95\% upper bound $3/N$ as an interpretable empirical bound. We do not call this a formal proof.

\subsection{RQ1: Safety under noisy observations}
The completed synthetic replay stresses one-sample and two-sample false positives, sustained/critical failure evidence, and intermittent evidence. The file-system matrix separately tests a genuine high-risk event while the remaining online-device count is too small for evacuation. Metadata-conflict injection and the complete Backblaze replay remain planned extensions of RQ1.

\input{tables/result-safety}

The completed replay shows the intended confirmation tradeoff directly. On 20,000 single-spike no-failure traces, fixed threshold drains in all 20,000 cases, whereas \autopilot{} drains in none. Across the three 20,000-trace failure cohorts, \autopilot{} completes protection before failure in 60,000/60,000 traces, matching fixed threshold and the oracle in this focused replay. Confirmation is deliberately finite rather than infallible: two consecutive false-positive observations satisfy the current two-observation rule, so \autopilot{} drains in 20,000/20,000 double-noise traces. This exposes the exact boundary of the current hysteresis instead of treating confirmation as a perfect noise filter.

The file-system-level matrix independently exercises critical drain, confirmed moderate-risk drain, insufficient-redundancy refusal, post-drain cooldown, rebalance after adding an empty device, and scrub repair after shard corruption. All 18/18 runs pass their scenario-specific postconditions. In particular, all three insufficient-redundancy runs remain observational rather than issuing an inadmissible drain.

\subsection{RQ2: Recovery effectiveness}
RQ2 separates \emph{acting early} from \emph{acting efficiently}. Reactive repair begins only at failure and therefore establishes the cost of waiting. Fixed threshold acts early but may move data for false alarms. Periodic maintenance can discover corruption but is not synchronized with device risk. Full \autopilot{} should occupy the middle ground: early enough to shorten risk exposure while avoiding migrations that are not justified by persistent evidence.

The completed failure/recovery matrix contains five repetitions each of clean write, interrupted write, interrupted rename, degraded read, self-heal, and Autopilot drain; all 30/30 runs pass their scenario-specific consistency and readback checks. The Autopilot matrix additionally contains three successful scrub-repair-corruption runs. These runs establish functional recovery behavior but do not yet provide the paired risk-exposure and data-movement measurements required for the RQ2 effect-size claim.

\subsection{RQ3: Foreground interference}
We run three FUSE workloads: (1) 4-KiB random read/write at a 70/30 ratio with four workers and queue depth 16, (2) 1-MiB sequential mixed I/O with two workers, and (3) an eight-worker small-file create/stat/remove workload. Each is measured alone and concurrently with scrub, rebalance, and proactive drain.

For fixed-budget baselines we sweep the maintenance window/rate setting from deliberately conservative to effectively unbounded values. The useful visualization is a Pareto frontier: foreground P99 slowdown on one axis and maintenance completion time or residual risk exposure on the other. We compare \autopilot{} with points that complete the same maintenance work, not merely with one hand-picked fixed limit.

\subsection{RQ4: Adaptation and ablation}
A 90-minute accelerated scenario changes conditions while one controller instance remains alive: normal load, foreground burst, transient health spike, recovery, controlled corruption, sustained device risk, safe drain, device addition, and placement skew. We record risk, evidence streak, chosen action, rejected alternatives, effective work budget, true foreground P99, files repaired or rewritten, and post-action verification on a common timeline.

We disable one controller mechanism at a time while retaining the same traces and primitive implementations. Two policy-level ablations are already complete. Removing confirmation changes the single-spike cohort from 0/20,000 to 20,000/20,000 false drains while leaving protection of the focused failure cohorts unchanged. Removing persistent risk memory has the complementary effect: it still ignores a one-sample spike, but protection on the intermittent-failure cohort falls from 20,000/20,000 to 0/20,000 because separated observations no longer accumulate evidence across controller cycles. These results isolate distinct roles for confirmation and persistence.

Cooldown, pressure-feedback, and rebalance-outcome ablations require the long-running and mounted-workload experiments and remain pending. The safety gate itself is not disabled because deliberately permitting known-unsafe mutations would turn the experiment into a different system; its rejection behavior is tested directly in RQ1.

\subsection{Reproducibility}
All synthetic traces are seed-driven. The repository now archives the completed raw JSON/JSONL artifacts under \texttt{data/raw/}, derived CSV summaries under \texttt{data/processed/}, and a manifest containing the exact ArgosFS revision and SHA-256 checksums. The current snapshot contains 18 Autopilot matrix runs, 30 failure/recovery runs, and 100,000 policy traces. Performance runs will preserve per-run latency logs rather than only aggregated percentiles. No reported count in the completed tables is copied manually from terminal output; the machine-readable summaries are retained beside the raw data. Appendix~\ref{app:reproducibility} describes the artifact layout.
