\section{Introduction}
\label{sec:introduction}

Storage maintenance is increasingly automated at the level of individual mechanisms. File systems and storage stacks can scrub data, reconstruct corrupted shards, migrate data away from a device, and rebalance after capacity changes. Device firmware and operating systems expose health counters, while large-scale studies show that some SMART signals correlate with impending failures even though individual failures remain difficult to predict reliably \citep{pinheiro2007failure,lu2020smarter}. A natural next step is to connect these mechanisms into a controller that observes the system and acts before failures become outages.

That connection is more dangerous than it first appears. A controller that drains a disk after one transient health spike can move terabytes unnecessarily. A controller that scrubs or rebalances as fast as possible can create severe foreground tail latency. A controller that migrates data while redundancy is already thin can turn an uncertain warning into an actual availability problem. These failure modes arise even when every underlying primitive is correct. The missing problem is therefore not only \emph{how to repair}, or \emph{how to predict}, but \emph{when an autonomous file system should act, which maintenance action it should choose, and how much work it should perform before observing the system again}.

Prior work has automated storage configuration and migration \citep{anderson2002hippodrome,sundaram2006migration}, monitored health and proactively replaced risky disks \citep{ma2015raidshield}, accelerated proactive erasure-code repair \citep{li2022fastpr}, and coordinated multiple reliability mechanisms within SSDs \citep{kim2019ssd}. Other systems tune redundancy from observed failure rates \citep{kadekodi2019heart}, and recent work shows that reliability-maintenance I/O itself is a major scheduling problem at hyperscale \citep{athlur2026declarative}. There are also full-process proactive-tolerance designs that explicitly connect collection, prediction, migration, and feedback \citep{yang2020proactive}. These systems establish that closed-loop storage management is useful; they also mean that a useful contribution cannot simply be the slogan \emph{SMART plus automatic migration}.

This paper focuses on a narrower control problem: \emph{safe, file-system-local maintenance when health evidence is imperfect and maintenance shares resources with foreground I/O}. We develop \autopilot{} inside \argosfs{}, an erasure-coded userspace file system. The controller exposes the existing maintenance primitives through one repeated observe--decide--act--verify loop. It retains evidence across cycles, introduces hysteresis between a warning and a destructive transition, computes a safety envelope from current file-system state, executes only bounded work, and feeds observed pressure and action outcomes into later cycles. An operator can switch the same mechanism among observe-only, safe, balanced, and aggressive policies without replacing the maintenance implementation.

The core design principle is \emph{safety before utility}. At each cycle, the controller first removes actions that violate structural preconditions or concurrency rules. It then chooses among the remaining actions and determines a bounded work budget. This separation is important: performance heuristics and health scores are allowed to be imperfect, but they do not get authority to bypass the file system's admissibility checks. When state is ambiguous, metadata changes conflict, or remaining redundancy is insufficient, the controller falls back toward observation rather than forcing progress.

We make the following contributions:
\begin{itemize}[leftmargin=*]
  \item We formulate autonomous file-system maintenance as a \emph{safety-constrained closed-loop control problem} over observe, scrub, rebalance, and proactive drain, separating uncertain evidence and utility from hard admissibility checks.
  \item We design persistent evidence, confirmation and cooldown hysteresis, bounded resumable maintenance, foreground-pressure feedback, post-action verification, and fail-closed conflict handling as a single controller rather than independent cron-style mechanisms.
  \item We implement the controller in \argosfs{} with durable controller state, dry-run explanations, deterministic decision logs, and integration with real scrub, rebalance, drain, FUSE, and erasure-coded repair paths. We document the current prototype boundary: the \autopilot{} command operates on the host-volume backend, while block-backed root pools share the data-plane primitives but are not yet controlled directly by this command.
  \item We define a reproducible evaluation that isolates the value of the controller from the value of its health signal. The comparison includes reactive, periodic, fixed-threshold, full \autopilot{}, oracle, and component-ablation policies under noisy traces, controlled corruption, device errors, workload shifts, and foreground I/O.
\end{itemize}
